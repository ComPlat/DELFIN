# Does a domain specialist being available change what an agent completes?

Pre-registered 2026-11-20, at `7abca4483`, before any run of either arm and
before the task sample was drawn. Nothing below may be rewritten; a change is
a dated addendum at the end of this file.

## 0. The limitation that comes first, because it bounds every number here

The five specialists this experiment switches on are **calculation
specialists**: `irc-checker`, `metal-smiles-builder`, `reactivity-department`,
`ts-finder`, `xyz-editor`. Their work is running and reading quantum-chemical
calculations.

The task corpus below is **code-connection work** — a capability the product
does not reach, to be connected or deleted. It is drawn mechanically, scored
objectively, and runnable tonight, which is why it was chosen. It is *not*
the work those five specialists exist for.

So this experiment answers: **does having domain specialists in the registry
change what an agent completes on code work, including code work in those
specialists' own modules?** It does **not** answer "is a specialist better
than a generalist at chemistry", and no number produced here may be quoted as
if it did.

That broader question needs a corpus of calculation tasks with checkable
ground truth. It does not exist in this repository, each such task is hours
of compute rather than minutes, and the ground truth for a transition state
is itself uncertain. Building that corpus is the follow-on, and is named here
so this result cannot be mistaken for it. This is the recurring defect of
this project written down in advance: *a mechanism that answers a
neighbouring question.*

## 1. The question, and what would falsify the hypothesis

**Hypothesis.** An agent that can see and delegate to domain specialists
completes more tasks than the same agent that cannot.

**Falsified if** the paired difference in completion rate is zero or negative,
or if the bootstrap interval over tasks covers zero — in which case the honest
statement is that the experiment could not distinguish the arms at this N,
and the specialist architecture rests on an assumption that remains untested.

A result against the hypothesis is reported identically to a result for it.
Every endpoint registered below is reported whatever it shows.

## 2. The one factor that varies, with the evidence

One switch: the user setting `agent.departments.reactivity` and
`agent.departments.structure`, both `false` in arm **G** and both `true` in
arm **S**. Nothing else differs — the brief text is byte-identical between
arms, the model is the same, the tree is the same, the task is the same.

Measured at `f02099cf9` with an isolated `HOME` holding only a settings file:

| | arm G | arm S |
|---|---|---|
| presets in the live registry | **12** | **17** |
| the five that differ | none | `irc-checker`, `metal-smiles-builder`, `reactivity-department`, `ts-finder`, `xyz-editor` |

The twelve present in both arms are identical by name.

**The confound this does not remove, stated rather than hidden:** arm S's
system prompt is longer, because the sub-agent tool's description derives from
the registry. The arms therefore differ in prompt bytes as well as in
available roles, and this experiment cannot separate "a specialist helped"
from "a longer tool description helped". The byte difference is recorded per
run and reported beside the result. A third arm — the five presets loaded but
`may_delegate_to` empty so they cannot be called — would separate the two,
and is **not** run here for budget reasons. It is the first follow-on.

An informational confound is excluded by construction: no domain context is
added to either brief. The critique that killed the first draft of this design
was that a specialist arm carrying a richer brief measures the brief.

## 3. The sample: drawn by query, never chosen

A person choosing tasks knows which domain the specialist covers, so no
person chooses. The work type is held **fixed** and only the domain varies, so
that arm and work type cannot be confounded.

The work type is the one `tests/test_every_capability_has_a_caller.py`
already defines: a capability in the product that nothing in the product
reaches — tier `nowhere` (nothing in `delfin/` or `tests/` names it) or
`test-only` (only the suite reaches it). The task sentence is always the same:
*connect this capability to the product, or delete it together with its
tests.*

Two pools, generated by the same scan over two scopes by
`scripts/ab_task_pools.py`:

- **`infra`** — `delfin/agent/`. Outside every specialist's domain, which the
  design requires the task list to include.
- **`chem`** — `delfin/tools/` and the chemistry modules of `delfin/`, by a
  rule written into that script rather than a hand-listed set of names.

Exclusions, applied in the script, each reporting how many it removed: a name
whose only non-definition mention is under `test-evidence/` or `docs/` (that
is documentation, not a caller); a name defined in a test file; a name in a
module absent from `origin/main`; a name under four characters (grep
-ambiguous).

`scripts/ab_draw_sample.py` draws the sample stratified — equal numbers from
each pool, and within a pool proportional to tier — from an explicit seed, and
writes the seed, the pool counts, the date and the tree's sha beside the list.
It refuses to re-draw without `--force` and prints the existing file's hash,
so a silent second draw is not possible.

**The sample is frozen before either arm runs.** If a pool holds fewer than
ten candidates, that is reported as a fact about the corpus and the design is
amended by addendum, not quietly rebalanced.

## 4. Endpoints, each with its denominator

**Primary — task completed.** Per attempt, binary, decided by
`scripts/ab_score.py`, which requires all of:

1. the capability is no longer a candidate of the scan — either a product
   caller now names it, or it is deleted. **Which of the two is recorded
   separately and never summed**: connecting and deleting are different
   outcomes.
2. the pre-existing tests of the touched files still pass, counted as
   passed / failed / **skipped separately** — a test turned into a skip is
   not a pass;
3. the scoring instrument was not touched. If the diff includes
   `test_every_capability_has_a_caller.py`, its fixture, any `scripts/ab_*.py`
   or a `conftest.py`, the attempt **scores zero** and the reason is recorded;
4. if the route was deletion, the capability's own tests are gone too. A
   deleted function whose tests were left behind red is not a completed task.

**Denominator: every attempt started.** A failure, a time-out, a refusal, a
crash and an empty result each score **zero**. None is excluded. The agent
cannot improve the rate by not finishing, and cannot improve it by writing or
weakening a test, because only tests that existed before the attempt and
failed at the baseline count.

**Secondary endpoints**, all pre-registered, all reported:

- **route** — connected versus deleted, per arm. An arm that deletes
  everything and an arm that connects everything have the same primary score
  and are not the same behaviour.
- **cost** — input tokens, output tokens, wall seconds, turns, per **attempt**
  and per **completed task**. A specialist that wins by spending three times
  as much is a different claim, and is reported as that claim.
- **collateral** — files touched outside the capability's own module, and
  whether the full fast suite is still green after the attempt.
- **specialist calls** — count and target, per arm. **Diagnosis only, never a
  target.** It can be driven to any value by writing "delegate" into a brief,
  so it explains a result and never scores one. Reported for arm G as well
  (self-delegation), because an endpoint reported for one arm only is an
  endpoint chosen after the fact.

## 5. N, stated in advance, and what it cannot detect

**16 tasks** (8 per pool) × **2 arms** × **2 repeats** = **64 attempts**.
Paired per task, bootstrapped over tasks, 10,000 resamples.

At 16 pairs this design can detect a difference of roughly **30 percentage
points** in completion rate. **It cannot detect 10.** If the true effect is
small, the interval will cover zero and the correct conclusion is "not
distinguishable at this N", not "no effect".

Budget: an agent run in the recent waves consumed 1–5 M input tokens, call it
3 M. 64 attempts is therefore of order 190 M tokens against a measured ceiling
of 50 M per key per day over three keys — two nights, not one. Repeats exist
because the same model on the same task does not do the same thing twice;
with one repeat a single stall would be indistinguishable from a real
difference.

## 6. Blind scoring and blind review

The runner writes each attempt into a directory named by an **opaque id**. The
arm lives in a separate mapping file that the scorer never opens. "Completed"
is decided mechanically; where a human or a reviewing agent judges anything,
that reviewer is given the diff and not the arm.

The scorer is itself an instrument, so it has tests that drive it against
fixtures — a capability connected, one deleted properly, one deleted with its
tests left behind, one where the instrument was touched, one where a test
became a skip — and each test must fail when its check is removed. An
instrument that reports success without doing its job is the defect class
this whole corpus is drawn from.

## 7. What will not be measured, and why

- **Number of landings, fixes, or PRs.** Driven by splitting work.
- **Any self-report of improvement**, from an agent or from me.
- **A pass rate under a judge being tuned at the same time**, as a target.
- **Anything computed by the same code path that produced the change.**
- **Specialist-call count as a success measure** — see §4.
- The sample is drawn **once**. If the first night's numbers are
  uncomfortable, the remedy is an addendum, not a redraw.

## 8. Provenance

The six design holes this protocol closes — the information confound, task
selection, gameable tests, who decides "landed", nondeterminism, and cost as a
second axis — were pointed out by the operator who ran the MANTA freeze, on
2026-11-20, against the first draft of this design. That draft would have
produced a number. The cases behind each are in
`DELFIN_RUNDE3/coord/goodhart-principles.md` of the coordination repository,
and the first draft's own flaw is §0 of this file.

**Not measured and not verifiable from here:** whether the specialist
architecture helps on the chemistry work the five specialists exist for (§0);
whether the result transfers to a different model; and whether the prompt-byte
confound of §2 accounts for any difference found.

## Addendum 1, 2026-11-20, before any arm ran

The apparatus was built against §3–§6 above and the build measured eleven
problems in them. Four change the protocol and are recorded here; nothing
above is rewritten. The pools and the sample below supersede the first draw,
which is superseded rather than deleted.

**The corpus, measured at `7abca4483`.** Pool `infra` 80 candidates (27
`nowhere`, 53 `test-only`) from 4,908 callables scanned; pool `chem` 78 (54
`nowhere`, 24 `test-only`) from 4,645. Neither is underpowered. The two pools
cover 64 % of the available work type: over all of `delfin/` there are 246
unmounted module-level callables, 158 fall in these pools and **88 fall in
neither** — non-chemistry files outside `delfin/agent/` (dashboard 29, manta
13, reporting 6, …). That is a property of the two scopes §3 fixed, stated so
no result is read as covering the repository.

**The scan is copied, not imported.** `tests/test_every_capability_has_a_caller.py`
and its 86-name fixture are not on `origin/main`; they live only on
`commit/a-commit-records-the-model-that-wrote-it`. Control for the copy: the
vendored functions reproduce that fixture's 86 names with identical tiers,
plus `set_commit_trailer_model`, which is unmounted on main and connected on
that branch. The live copy of the instrument is therefore
`scripts/ab_task_pools.py`, which is why it is on the untouchable list of
check 3.

### Change 1 — the allocation is balanced, not proportional

§3 said "within each pool proportional to tier". That re-introduces the
confound the two pools exist to remove: the tier mixes are near-opposites
(infra 34 % `nowhere`, chem 69 %), and tier plausibly predicts difficulty — a
`test-only` capability has a test pinning its behaviour and a caller to find,
a `nowhere` one is more often simply dead. The first draw shows the effect
directly: infra 3/7, chem 7/3. Domain would have been confounded with tier.

The allocation is therefore **5 `nowhere` + 5 `test-only` from each pool**.
Both pools can supply it, so no power is lost. Tier now varies within arm and
is reported as a covariate.

### Change 2 — the primary endpoint requires an AST-visible call site

§4 check 1 could be satisfied by a string literal. The scan counts a name in
a string as a reference, deliberately, because name-based dispatch is real in
this codebase and ignoring it called two live functions unreachable. But that
makes `DISPATCH = ("orphan_capability",)` a passing attempt, which is exactly
"something the agent could write itself".

So the endpoint splits, and both halves are reported:

- **primary** — connected by an **AST-visible call site** in the product, or
  deleted together with its tests;
- **secondary** — the string-literal-inclusive variant, i.e. the rule as
  first registered.

The string-literal route stays in the record because an attempt that connects
a capability through a genuine dispatch table is correct work. The **per-arm
count of attempts where the two variants disagree** is itself a reported
result about the corpus.

### Change 3 — check 3 needs one narrow exception, or it scores every correct infra attempt zero

Both routes force an edit to `tests/fixtures/unmounted_capabilities.txt`,
because its ratchet test goes red until the name is removed. As first
registered, check 3 would have charged every *correct* `infra` attempt a zero
— and "no difference between the arms" is the result this protocol was most
prepared to believe.

The exception is exactly this: the fixture may **lose** this capability's one
line and nothing else — zero added lines, zero header changes, removed names
equal to this capability alone. **An added line still scores zero**, because
adding a line is how an orphan would be excused rather than fixed. Every
other file on the untouchable list stays untouchable.

### Change 4 — the `documented_only` exclusion is removed

Its justification was backwards. The scan never reads `docs/`, so a
documented name is already tier `nowhere`; as a filter it removed a candidate
*for being documented*, which treats a doc mention as evidence of an entry
point. Removed. It had removed one name, `describe_mlp_backends`, which is
back in `chem`.

The other three exclusions removed **0** each — `module_absent` is 0 by
construction, since the pools are scanned from the same tree — and they are
kept with their measured zeros, because a filter that removed nothing and
says so is readable and a later corpus may need them.

### Recorded, not acted on

- **Check 2 is vacuous for two of the drawn tasks.** `ensemble_summary`
  (`delfin/manta/_ensemble_dispatch.py`) and `validate_control_file`
  (`delfin/config.py`) have no consuming suite for their defining file. Both
  stay in the sample; for those two the score rests on checks 1, 3 and 4
  only, and that is reported with their rows rather than averaged away.
- **Two unreachable twins hide each other.** A name defined twice is never a
  candidate, because each twin counts as a mention of the other. This is a
  limitation of the original instrument as much as of this one.
  `candidates_with_a_twin` is reported; it is currently none.
- **The chemistry rule's recall.** The rule is per file, never per package —
  a package verdict calls all 609 `delfin/agent` files chemistry because five
  of them import rdkit or ase. Its absolute floor costs recall on small
  chemistry modules, among them `ts_finder.py`, `fukui.py`, `ir_spectrum.py`
  and the other spectrum modules. `ts-finder` is one of the five presets the
  switch adds, so a `chem` pool that excludes the module a specialist is
  named after measures the wrong thing. An S3 clause is being measured; if no
  rule separates those files from a 20-word banner module, the gap stays and
  stays documented, because a rule that cannot be stated is worse than a gap
  that is written down.
- **Route mix.** Deletion is almost always cheaper than connection, so an arm
  that deletes everything scores 1 on everything, guarded only by check 4 and
  the consuming suites. The route mix was already a registered endpoint (§4);
  added here: **ten raw diffs, chosen at random rather than picked, are read
  before any aggregate of this experiment is believed.**

### Blindness and mutation evidence, as built

No arm, role or model argument reaches the scorer, asserted by a test over
its parser's option strings. Exactly two files are opened inside an attempt
directory, by fixed name; everything else is listed in `ignored_files` and
never read. A manifest key outside the allowlist, or arm vocabulary anywhere
in the manifest, **refuses with no score emitted** — an apparatus defect must
not be charged to the agent as a zero. The log is projected onto
`{ts, input_tokens, output_tokens, type, role}` at the read, with a count of
discarded fields rather than their names. A missing cost figure is `null`.

The instrument's own checks were mutation-tested: 25 mutations, 25 caught.
**Four tests passed their first mutation and were rewritten** — one rested on
a sibling clause of the same `and`, one on the arm-word check instead of the
key allowlist, one could not observe the log projection from outside, one on
the allocator's arithmetic rather than the pool refusal it names. That
rewrite loop is the reason to run a mutation harness instead of asserting
that tests are attached.

## Addendum 2, 2026-11-20, still before any arm ran

Building the four changes of Addendum 1 found six more problems, two of them
in the registered text itself. Corrections first, then the limits that stay.

### Correction A — the registered N was wrong in §5

§5 says **16 tasks (8 per pool)**. Change 1 of Addendum 1 and both draws use
**10 per pool, 20 tasks**. The registered number and the drawn number
disagreed in the protocol, which is the one thing a protocol exists to
prevent. **N is 20 tasks** — 10 per pool, 5 per tier per pool — × 2 arms ×
2 repeats = **80 attempts**, of order 240 M tokens at the measured 3 M per
run, so three nights rather than two. The resolution statement of §5 stands:
20 pairs can show roughly 30 points and cannot resolve 10.

### Correction B — the corpus figures of Addendum 1 are superseded

| | Addendum 1 | now |
|---|---|---|
| `infra` | 80 (27 / 53) | **80 (27 / 53), name for name** |
| `chem` | 78 (54 / 24) | **99 (70 / 29)** |
| in neither pool | 88 | **67** |
| unmounted over all `delfin/` | 246 | 246 |
| exclusions that removed anything | 1 | **0** |

`infra` is identical name for name: 25 rather than 18 `delfin/agent/` files
are now classed chemistry and leave it, but none held an `infra` candidate.
Sample sha256 `f9d9cdd2d9f17f66…`, superseding `225e5772d1dc73bd…`, seed
20261120, `allocation_rule: balanced`; the new file records the replaced hash
and the time. Pools `e8a484b8f2987237…`, scanned at `0eb187ff9`.

### Correction C — check 2 is vacuous for one task, not two

Addendum 1 named `ensemble_summary` and `validate_control_file`; both are
tied to the superseded sample and are no longer drawn. Re-measured over all
20 new tasks, **exactly one has no consuming suite: `describe_mlp_backends`**
(`delfin/mlp_tools/__init__.py`) — the candidate Change 4 brought back. For
that row the score rests on checks 1, 3 and 4, reported with the row.

### Correction D — a self-call does not connect anything

An attempt can add `return orphan_capability(x)` **inside the orphan's own
body**: the call site is AST-visible under `delfin/`, so `capability_resolved`
becomes true while nothing reaches it. That is the exact shape Change 2 was
written to close, in a place Change 2 did not look, and it cannot occur at
baseline — a recursive function is never a candidate, because the self-call
counts as a mention — so only an attempt can create it.

**A call site inside the definition's own function node does not count.**
This narrows a registered endpoint, which is why it is recorded here before
any arm ran rather than applied silently.

### Added as diagnosis, not as score

"Connected" is narrower than "called": a capability wired in by decorator,
passed as a callback, or placed in a dict of function objects is genuinely
connected and scores 0 on the primary (the secondary catches it, together
with string literals). A **third reading** — any non-string `ast.Name` or
attribute load of the capability in non-test product code — is recorded per
attempt as a diagnostic field. It is not the score: adding a third scoring
rule after the first draw is how an endpoint gets chosen for its answer.

### Limits that stay, written down rather than fitted away

- **The rule now admits the specialist's own module; the corpus still has
  nothing there.** `ts_finder.py`, `ir_spectrum.py`, `nmr_spectrum.py`,
  `uv_vis_spectrum.py` and `turbomole_version.py` hold **zero** unmounted
  candidates. Only `fukui.py` contributes two. So Addendum 1's motivation is
  satisfied as a rule while the measurable effect on drawn work from a
  specialist's own module is **nil**. This result may not be read as "the
  experiment now covers the specialists' modules".
- **The `chem` pool is not pure.** `dashboard/__init__.py` passes S3 at 1.6 %
  chemistry identifiers and brings 4 candidates, 3 of them git-branch
  helpers. No threshold separates it from `fukui.py` at 1.2 %, so the share
  cannot be raised to refuse it, and a word-count cap would drop ~10 genuine
  MANTA chemistry files. Each drawn row carries its own name and can be
  checked.
- **Recall limit.** Of the 67 still unpooled, about ten are MANTA
  geometry-repair candidates that are chemistry by subject with zero
  vocabulary hits: the vocabulary carries program, method and observable
  names, not structure words — chelate, isomer, ligand, torsion. Widening it
  would move the pools again and is not done.
- **`allocate` is off by one for an odd split with three or more strata**,
  refusing a feasible largest-remainder allocation. Harmless at two tiers and
  10 per pool; it is an instrument defect and is fixed rather than tolerated.

### What the instrument's own build taught

The S3 fragmenter could not see upper-case acronyms — `ORCA` split to
`O`,`R`,`C`,`A`, and `SMILES_RE` carried no chemistry fragment. That is also
why one mutation survived its first harness run: **the banner-control test
passed for the wrong reason, seeing nothing either way.** Taking the
upper-case run first changes the verdict on 22 files, all admitting, and the
test was rewritten so it fails under that mutation rather than the count
being accepted.

And the instrument built to find uncalled callables had produced one of its
own — `is_chemistry_file`, orphaned by Change 3 and deleted.

Instrument state: **42 tests passed, 35 mutations applied, 35 caught.**

## Addendum 3, 2026-11-20, a prediction recorded before the run

A prediction written down before the data so the measurement can refute it.
It is not a hypothesis of the protocol and no endpoint is changed; it is on
record so that agreement afterwards cannot be mistaken for evidence.

### The prediction

> **A second independent reviewer wins clearly. A domain specialist against
> a generalist comes out flat or marginal.**

### Why, from the day this was written

Six defects were found in this author's own work on 2026-11-20 by delegated
agents: four in the specialist foundation itself, an endless loop in a
shell-word scanner that would have hung every agent command containing
`2>&1`, and eleven problems in the first draft of this protocol.

**Every one was found by independence, not by domain knowledge.** A
chemistry specialist would not have found a loop in a shell-word scanner.
The common factor was that somebody else looked, with the same files and
without the author's conclusion.

So the lever may not be the number of specialist roles but **whether a
second agent looks at all** -- which would be an uncomfortable answer for
the direction this architecture is being built in, and is the reason to
write it down rather than discover it as a feeling later.

### What would refute it

The `chem` arm completing materially more than the `infra` arm within arm S,
while arm G shows no such gap: that would be domain specialisation doing
work independently of a second pair of eyes. A flat result everywhere
refutes nothing and means the design could not distinguish the two.

### The framing this prediction implies, and why both are kept

"Which one wins" is the wrong question, because the two are not measured on
the same axis. Three axes, measured separately and never summed:

1. **Outcome** -- what gets completed. This protocol's primary endpoint. The
   prediction above is about this axis and expects it to be flat.
2. **Confinement** -- what the agent *can* touch. Here a specialist is not a
   better thinker but a **smaller one**: `metal-smiles-builder` declares 7
   tools and `xyz-editor` 23, against a generalist's full surface, and a
   preset's `write_globs` can be refused entry to the security core
   entirely. That is a measurable property of the preset and needs no A/B --
   blast radius, refused actions, scope violations.
3. **Cost** -- tokens and wall seconds per completed task, the registered
   second axis of section 4. Note what the prefix-cache measurement of the
   same day does to the naive version of this argument: the tool schema is
   11,718 tokens per request, and on a host that caches a stable head a
   repeated large head costs almost nothing (measured 31x on KIT), while on
   a host that routes around its own cache it costs full price every turn.
   So "a specialist is cheaper because it sends fewer tools" is
   **host-dependent** and must be measured per host, not assumed.

A generalist is kept because the work does not arrive sorted by domain, and
most of it is not chemistry: of 246 unmounted capabilities in this
repository, 80 are agent infrastructure. A specialist is kept for axis 2,
which is a security property rather than a quality one, and which holds
whatever axis 1 shows.

If the prediction is right, the conclusion is **not** "drop the
specialists". It is that their value was on the axis nobody was measuring,
and that the roster should grow for confinement and be judged on
confinement -- while the thing to invest in for outcome is that a second
agent reviews at all.

## Addendum 4, 2026-11-20, task validation fixed before the tasks were read

Written before any row of the sample was looked at, so the rubric cannot be
fitted to what the rows turned out to be.

### Why this is added

The lesson the established benchmarks paid for: **the task set is an
instrument and has to be validated.** SWE-bench Verified exists because 93
developers screened 1,699 instances and kept 500 where the issue was not
underspecified *and* the tests were appropriately scoped; the three failure
modes were an underspecified task, an environment where the tests fail
whatever the agent does, and tests scoped too narrowly or too broadly. It is
still contested — one audit rates it flawed, a study found 7.8 % of accepted
patches failing the developers' own tests, and a SWE-Bench Pro
recommendation was retracted in July 2026 after about 30 % of its tasks were
judged broken.

This protocol mechanised **selection** (§3) to remove the bias of a person
choosing tasks in a domain they know. That is a different problem from
**validity**, and mechanising the first does nothing for the second. Twenty
rows were drawn and nobody had read them.

### The rubric, fixed now

Each drawn row gets exactly one verdict, with a written reason:

- **usable** — a competent agent can tell from the code what connecting this
  capability would mean, or that deleting it is right; and checks 1–4 bite.
- **underspecified** — the intended call site is not knowable from the code,
  so "connect it" has no determinable answer and the agent is graded on a
  guess.
- **mis-scoped** — a check does not measure the work. Includes: no consuming
  suite, so check 2 is vacuous; a capability that is a published entry point
  for callers outside this repository, where deleting it is wrong and
  connecting it is meaningless; a capability whose own tests cannot be
  located, so check 4 cannot be applied to the deletion route.
- **blocked** — the work cannot be done or checked on the host the arms run
  on: it needs a device, a licensed program, or a file the person has
  reserved to themselves (the security core).

### What happens to a row that is not usable

It is **replaced from the same pool, same tier, by the next row the same
seed produces**, and both the removed row and its replacement are recorded
with the verdict and the reason. Rows are not silently dropped: a sample
that shrinks is a denominator the experiment controls, which is the trap
this whole protocol is written against.

If more than **5 of 20** rows are not usable, the corpus — not the sample —
is the finding, and the experiment does not run until that is reported.

### Two validators, because one of them has a prediction on record

The author of this protocol has committed a prediction (Addendum 3) and is
therefore not a disinterested judge of which tasks are fair. So:

- the author validates all 20 rows and records a verdict and reason for each;
- **a second agent validates the same 20 blind** — given the rows and this
  rubric, and **not** the author's verdicts, the prediction, or which pool a
  row came from;
- **every disagreement is listed in the result.** A row both call unusable is
  replaced. A row they split on is replaced as well, and the split is
  reported: treating a contested row as usable would let the author's
  judgement decide the sample, and treating it as fine without saying so
  would hide that the two instruments disagree.

The agreement rate between the two validators is reported as a property of
the rubric. A rubric both can apply the same way is worth something; one they
apply differently was a matter of taste and must be said to have been.

### Three further corrections from the same reading

- **The scaffold is recorded in every artefact.** The field's advice is to
  log framework version, plugins, routing and tool versions; this protocol
  recorded `tree_sha`, model and host but **not the swarm harness sha**. The
  harness in use is three weeks behind `main` and does not contain the five
  presets arm S depends on, so without the harness sha an artefact cannot be
  told from one produced by a tree where arm S was impossible. It is added to
  the sample, the attempt manifest and the score record.
- **`pass^k` beside `pass@k`.** The convention is shifting to requiring *all*
  k attempts to succeed rather than any. Both are reported: `pass@2` (either
  repeat completed) and `pass^2` (both did). The second is the stricter
  reliability statement and is the one quoted in any summary sentence.
- **Repeats stay at 2, and the price is stated.** Three to five repeats is
  the recommended range; 20 tasks × 2 arms × 3 repeats is 120 runs against a
  measured ceiling of about 50 runs a day over three keys, so 3 repeats costs
  the whole weekend and leaves nothing for the review gate or the capability
  debt. 2 repeats is chosen **knowing it is below the recommendation**, which
  is a different thing from not knowing.

### Cost is plotted, not appended

Accuracy against cost per completed task, per arm — not cost as a line at the
end of the table. Per-task cost is reported to vary by a factor of order
hundreds across scaffolds, which makes an accuracy number without its cost
close to meaningless.

## Addendum 5, 2026-11-20: the threshold fired. The corpus is the finding.

Two validators judged the same 20 rows against the rubric of Addendum 4.
Addendum 4 fixed the consequence in advance, and it applies:

> If more than **5 of 20** rows are not usable, the corpus — not the sample
> — is the finding, and the experiment does not run until that is reported.

**Nine of twenty.** The experiment does not run.

### The two readings

| | validator A (protocol author) | validator B (blind) |
|---|---|---|
| usable | 18 | **11** |
| underspecified | 0 | **4** (rows 1, 5, 6, 17) |
| mis-scoped | 0 | **2** (rows 4, 7) |
| blocked | 1 (16) | **3** (10, 14, 16) |
| outside the rubric | 1 (14) | 0, but row 1 wants a fifth verdict |

```
both usable        11   rows 2 3 8 9 11 12 13 15 18 19 20
both unusable       2   rows 14 16
split               7   rows 1 4 5 6 7 10 17
agreement       13/20 = 65 %
to replace          9   (both-unusable + every split, per Addendum 4)
```

**Agreement is 65 %**, and that is a property of the rubric, not of the
rows. A rubric two careful readers apply the same way is worth something;
one they apply differently on a third of the set was partly a matter of
taste, and Addendum 4 said it would have to be said to have been.

Validator A was wrong on six of the seven splits, and in a consistent
direction: **A checked the code and did not check the documentation.**
Where A read a signature and a docstring, B ran `git grep` over `docs/`,
`website/` and `.gate/`, and ran `auto_guard.protected_reason` rather than
reasoning about it.

### What B found, which is the actual result

- **Row 1 `_max_heavy_bond_order`** — the comment A read as "retained"
  says, in full, that this helper is kept *as reference for a future
  explicit M=O / M≡N multiple-bond layer*. Connecting means building a
  feature that does not exist; deleting reverses a written decision. A read
  the same comment and called the row usable.
- **Row 4 `describe_mlp_backends`** — `docs/mlp.md:149` documents
  `from delfin.mlp_tools import describe_mlp_backends` **for users**. It is
  a published entry point: deleting is wrong, and connecting is meaningless
  because the product already calls the wrapped
  `registry.describe_backends()` directly.
- **Row 7 `est_reference_comparison`** — its real caller is
  `.gate/practice/grade_es1.py`, **uncommitted by the operator's own
  ruling**, so the caller is outside the repository by design and three
  sibling functions are unmounted for the same reason.
- **Row 10 `write_co2_scan_opi_input`** — `opi` is not importable in the
  repository's own `delfin-ci` environment, and both files that exercise
  the writer die on a module-level `importorskip("opi")`.
- **Row 14 `expected_digest`** — `auto_guard.protected_reason(
  "delfin/agent/principles_guard.py")` returns a reason; B **ran it**. The
  file is the security core and both routes require editing it. A had
  called this row "already landed", which is also true and is the lesser
  fact.
- **Rows 6 and 17** — `check_goat_e2e` and `distill_for_shipping` are
  documented, operator-facing entry points where deletion is wrong and **no
  consumer exists in the product at all**, so connecting means inventing
  the surface.

### Why the corpus is wrong, and it is the same shape as everything else today

The population was defined by a tree scanner **whose own docstring warns**
that "a function reached through `getattr`, **a documented entry point for
outside users**, and a module loaded by filename from data all look
identical to it". Rows 4, 6, 7 and 17 are exactly that case.

And the task sentence — *connect this capability to the product, or delete
it together with its tests* — **presupposes that the finding is a defect**.
On roughly a third of the rows it therefore asks an agent to damage
working, documented code, and then scores whether it did.

So the corpus answers a neighbouring question: **"is this name unreferenced
by a tree scan" is not "is this capability unmounted"**. That is the
recurring defect of this project, this time in the instrument that was
built to measure it.

### Two defects in the rubric itself, neither anticipated

1. **No verdict for "the code documents a decision to keep this
   unconnected."** Row 1 is precisely that, and both offered actions are
   wrong. A fifth verdict is needed: **declined** — the code records a
   decision to leave the capability unconnected. Row 16 is a milder
   instance, where the suite says the wiring is the person's to do.
2. **A check can be *inverted* rather than vacuous.** Row 16's wiring tests
   carry three `xfail(strict=True)` marks whose reason reads "operator
   wiring pending". An agent that **correctly** connects the capability
   turns three xfails into xpasses, and strict mode reports an xpass as a
   **failure**. The rubric's mis-scoped clause anticipated a check that
   measures nothing; it did not anticipate one that punishes the right
   answer.

Two further points, recorded: checkability is **not uniform** — the ten
`delfin/agent/` rows sit under the baseline ratchet, which must shrink when
a name is connected or deleted and is therefore a crisp automatic check,
while rows 1–10 have no such invariant, so one grader applying one standard
to all 20 would be measuring two different things. And "its own tests
cannot be located" and "it has no own tests at all" are different states
that the rubric merged; ten rows have no tests, which makes "delete it
together with its tests" trivially satisfied.

### What has to change before this experiment runs

Not a redraw from the same pools: the pools themselves admit the four
shapes above. The pool generator needs three mechanical exclusions, each
testable:

- a name mentioned under `docs/`, `website/` or any published reference —
  **a documented entry point is not an orphan**, and the old
  `documented_only` filter was deleted in Addendum 1 for a justification
  that pointed the other way;
- a name whose defining file `auto_guard.protected_reason` answers for —
  the security core, decided by running the product's own function rather
  than by a path list;
- a name whose consuming suite is gated by `importorskip`, so the check
  cannot run on the host the arms run on.

Plus the fifth verdict, the inverted-check case, and a pre-flight that
checks each drawn row against **every open PR** and not only against
`main` — the sample went stale inside a day because 17 PRs landed while it
sat.

### What this costs and what it bought

It costs the weekend's A/B: 80 runs are not started.

It bought the reason not to trust them. The threshold was written into the
protocol before the sample was read, two validators were used because the
author had a prediction on record, and the rule fired on the author's own
experiment. An A/B run on this corpus would have produced a clean number
with a confidence interval, and about a third of it would have been
measuring whether an agent will delete documented, working code when a
brief tells it to.

## Addendum 6, 2026-11-20: the rebuilt corpus, and what it does not cover

Addendum 5 retired the first sample. The pools were rebuilt with the three
exclusions it required plus four instrument changes. Measured at
`e452ac009`:

| | before | after | `nowhere` | `test-only` |
|---|---|---|---|---|
| `infra` | 80 | **66** | 24 | 42 |
| `chem` | 99 | **90** | 68 | 22 |

Both clear ten per tier, so a balanced 5 + 5 draw holds with margin.
**Nothing here is blocked by power.** 179 → 156 rows.

| exclusion | removed | infra | chem |
|---|---|---|---|
| documented entry point | 7 | 5 | 2 |
| security core | 12 | 7 | 5 |
| suites cannot run here | 2 | 0 | 2 |
| suite punishes the fix | 2 | 2 | 0 |
| the three that fired on nothing | 0 | 0 | 0 |

The security core is decided by **loading and running
`auto_guard.protected_reason` from the scanned tree**, under a private
package name so an already-imported `delfin` cannot answer, and the
answering file is recorded. When that function cannot be loaded the
exclusion removes nothing **and says so with the reason** — an exclusion
that silently removes nothing looks exactly like one that found nothing.

Two of the four rows the validation named are **not** excluded, and both
corrections are the apparatus's, against my reading:

- `est_reference_comparison` stays. Its caller is in uncommitted `.gate/`,
  which no reference directory sees, so it is still mis-scoped and the
  documented-entry-point rule does not reach it.
- `write_co2_scan_opi_input` stays. Two of the three suites covering its
  module die on `opi`; **the third runs.** The validation looked at the two
  that die.

### What the experiment measures, stated narrowly

The work type is unchanged — an unreached module-level callable, to be
connected or deleted. Exclusion 1 does not narrow it; it **restores** it,
because a documented entry point was never an unreached capability: it is
reached from outside the repository and the scanner cannot see out.

The other three narrow the population in one direction, and it is not the
work that is excluded but the **measurement**. So, registered:

> The arms are measured on an unreached capability **that no published
> reference names, that is not in the security core, and whose checks can
> run here and do not punish the fix.**

That is narrower than §3 declares, by **23 of 179 rows**, and those are not
noise: they are four kinds of work the arms will never be asked to do. They
are a **named, counted part of the corpus this experiment does not cover**,
and no result may be read as covering them.

### Three changes the rebuild made necessary

**A. The task sentence offers a third option.** It still presupposed the
finding was a defect. The `declined` signal reports four candidates and one
is the real case — `_max_heavy_bond_order`, whose comment sits **326 lines**
below its definition and keeps it as reference for a future multiple-bond
layer. Without a third option an arm that answers honestly scores zero, so
the sentence becomes:

> connect this capability to the product, or delete it together with its
> tests — **or report that neither is right, with the evidence.**

The third answer is scored as a completion when the evidence holds, and the
`declined` candidates are reported per row **for a person**: the signal
catches one real case in four, and three of its four hits are comments
about how a test harness uses the function, which is precisely why the
mechanism may not decide.

**B. Rows are not averaged across two instruments.** With the resolver
fixed, **15 of 156 rows have no consuming suite at all**, so checks 1, 3
and 4 decide them while the rest are decided by four. And every `infra` row
additionally sits under the baseline ratchet, a crisp automatic check that
`chem` has no equivalent of. Each row therefore carries its
`consuming_suites` count and whether it is under the ratchet, and the
result reports **by instrument class, not pooled**. One grader applying one
standard to all 156 would be averaging two different measurements.

**C. The two pools were filtered by different rules**, and that is stated
rather than left to be noticed: `infra` lost 14 of 80 and `chem` 9 of 99,
with the security core almost entirely `infra` and the unrunnable suites
entirely `chem`. The surviving work type is the same in both; if anything
correlates with difficulty, the asymmetry of the filters is a candidate
explanation and must be available to whoever reads the result.

### The pre-flight, and the defect it had

Every drawn row is checked against **every open pull request** — a sample
drawn from `main` goes stale at the speed of the landing queue, and 17 PRs
landed the day the first one was drawn. A pre-flight that cannot run
**refuses the draw**; skipping it records the gap in the sample.

Its first version **refused 18 rows because of this protocol document.**
Scanning whole diffs, 21 of 156 rows were refused and 18 came from the
pull request carrying this pre-registration and its addenda, which name
rows in prose and decide none of them. *A pre-flight that refuses a row
because the experiment's own write-up discusses it is measuring the
write-up.* Fixed: a changed line counts only under `delfin/` or `tests/`,
with both diff headers read so a deletion is still attributed. 21 → 3.

Live against the 8 open pull requests, **3 of 156** rows are refused —
`_redirect_targets_safe` (#834), `generate_stub` and `serve_request`
(#832), all `infra` — leaving `infra` 63 (23/40) and `chem` 90 (67/23).

### Two defects the apparatus found in itself, both the same shape

- **The scan was reading the apparatus's own test file.** Comparing two
  scans of one tree, `_max_heavy_bond_order` moved from `nowhere` to
  `test-only` with no test of it anywhere — the apparatus's test docstring
  names it, and `tests/` is scanned as text. `expected_digest` is named six
  times there for the same reason. That file now joins the baseline fixture
  in the skip set. **This is the instrument measuring itself one step
  further out than the guard already in place, and it would have changed a
  stratum in the draw.**
- **The resolver's cause is the mapping, not the cap.** A package's
  `__init__.py` has the stem `__init__`, which is in the unsearchable set,
  so the import search was skipped entirely and the answer came back empty
  — a cap truncates a non-empty answer and cannot produce an empty one.
  `delfin/mlp_tools/__init__.py` resolved to 0 suites and now resolves to
  12 of the 33 files naming `mlp_tools` on an import line. Addendum 5
  recorded the under-reporting; this is its cause.

Instrument state: **55 tests, 66 mutations applied, 66 caught.** One
mutation reported `SETUP FAIL` rather than failing, because restructuring
the diff parser moved the line it anchored on — an unmeasured check, not a
passing one. Re-anchored and driven.
