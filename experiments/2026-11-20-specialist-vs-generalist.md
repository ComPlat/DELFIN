# Does a domain specialist being available change what an agent completes?

Pre-registered 2026-11-20, at `7abca4483`, before any run of either arm and
before the task sample was drawn. Nothing below may be rewritten; a change is
a dated addendum at the end of this file.

## 0. The limitation that comes first, because it bounds every number here

The five specialists this experiment switches on are **calculation
specialists**: `irc-checker`, `metal-smiles-builder`, `reactivity-department`,
`ts-finder`, `xyz-editor`. Their work is running and reading quantum-chemical
calculations.

The task corpus below is **code-connection work** — a capability the product
does not reach, to be connected or deleted. It is drawn mechanically, scored
objectively, and runnable tonight, which is why it was chosen. It is *not*
the work those five specialists exist for.

So this experiment answers: **does having domain specialists in the registry
change what an agent completes on code work, including code work in those
specialists' own modules?** It does **not** answer "is a specialist better
than a generalist at chemistry", and no number produced here may be quoted as
if it did.

That broader question needs a corpus of calculation tasks with checkable
ground truth. It does not exist in this repository, each such task is hours
of compute rather than minutes, and the ground truth for a transition state
is itself uncertain. Building that corpus is the follow-on, and is named here
so this result cannot be mistaken for it. This is the recurring defect of
this project written down in advance: *a mechanism that answers a
neighbouring question.*

## 1. The question, and what would falsify the hypothesis

**Hypothesis.** An agent that can see and delegate to domain specialists
completes more tasks than the same agent that cannot.

**Falsified if** the paired difference in completion rate is zero or negative,
or if the bootstrap interval over tasks covers zero — in which case the honest
statement is that the experiment could not distinguish the arms at this N,
and the specialist architecture rests on an assumption that remains untested.

A result against the hypothesis is reported identically to a result for it.
Every endpoint registered below is reported whatever it shows.

## 2. The one factor that varies, with the evidence

One switch: the user setting `agent.departments.reactivity` and
`agent.departments.structure`, both `false` in arm **G** and both `true` in
arm **S**. Nothing else differs — the brief text is byte-identical between
arms, the model is the same, the tree is the same, the task is the same.

Measured at `f02099cf9` with an isolated `HOME` holding only a settings file:

| | arm G | arm S |
|---|---|---|
| presets in the live registry | **12** | **17** |
| the five that differ | none | `irc-checker`, `metal-smiles-builder`, `reactivity-department`, `ts-finder`, `xyz-editor` |

The twelve present in both arms are identical by name.

**The confound this does not remove, stated rather than hidden:** arm S's
system prompt is longer, because the sub-agent tool's description derives from
the registry. The arms therefore differ in prompt bytes as well as in
available roles, and this experiment cannot separate "a specialist helped"
from "a longer tool description helped". The byte difference is recorded per
run and reported beside the result. A third arm — the five presets loaded but
`may_delegate_to` empty so they cannot be called — would separate the two,
and is **not** run here for budget reasons. It is the first follow-on.

An informational confound is excluded by construction: no domain context is
added to either brief. The critique that killed the first draft of this design
was that a specialist arm carrying a richer brief measures the brief.

## 3. The sample: drawn by query, never chosen

A person choosing tasks knows which domain the specialist covers, so no
person chooses. The work type is held **fixed** and only the domain varies, so
that arm and work type cannot be confounded.

The work type is the one `tests/test_every_capability_has_a_caller.py`
already defines: a capability in the product that nothing in the product
reaches — tier `nowhere` (nothing in `delfin/` or `tests/` names it) or
`test-only` (only the suite reaches it). The task sentence is always the same:
*connect this capability to the product, or delete it together with its
tests.*

Two pools, generated by the same scan over two scopes by
`scripts/ab_task_pools.py`:

- **`infra`** — `delfin/agent/`. Outside every specialist's domain, which the
  design requires the task list to include.
- **`chem`** — `delfin/tools/` and the chemistry modules of `delfin/`, by a
  rule written into that script rather than a hand-listed set of names.

Exclusions, applied in the script, each reporting how many it removed: a name
whose only non-definition mention is under `test-evidence/` or `docs/` (that
is documentation, not a caller); a name defined in a test file; a name in a
module absent from `origin/main`; a name under four characters (grep
-ambiguous).

`scripts/ab_draw_sample.py` draws the sample stratified — equal numbers from
each pool, and within a pool proportional to tier — from an explicit seed, and
writes the seed, the pool counts, the date and the tree's sha beside the list.
It refuses to re-draw without `--force` and prints the existing file's hash,
so a silent second draw is not possible.

**The sample is frozen before either arm runs.** If a pool holds fewer than
ten candidates, that is reported as a fact about the corpus and the design is
amended by addendum, not quietly rebalanced.

## 4. Endpoints, each with its denominator

**Primary — task completed.** Per attempt, binary, decided by
`scripts/ab_score.py`, which requires all of:

1. the capability is no longer a candidate of the scan — either a product
   caller now names it, or it is deleted. **Which of the two is recorded
   separately and never summed**: connecting and deleting are different
   outcomes.
2. the pre-existing tests of the touched files still pass, counted as
   passed / failed / **skipped separately** — a test turned into a skip is
   not a pass;
3. the scoring instrument was not touched. If the diff includes
   `test_every_capability_has_a_caller.py`, its fixture, any `scripts/ab_*.py`
   or a `conftest.py`, the attempt **scores zero** and the reason is recorded;
4. if the route was deletion, the capability's own tests are gone too. A
   deleted function whose tests were left behind red is not a completed task.

**Denominator: every attempt started.** A failure, a time-out, a refusal, a
crash and an empty result each score **zero**. None is excluded. The agent
cannot improve the rate by not finishing, and cannot improve it by writing or
weakening a test, because only tests that existed before the attempt and
failed at the baseline count.

**Secondary endpoints**, all pre-registered, all reported:

- **route** — connected versus deleted, per arm. An arm that deletes
  everything and an arm that connects everything have the same primary score
  and are not the same behaviour.
- **cost** — input tokens, output tokens, wall seconds, turns, per **attempt**
  and per **completed task**. A specialist that wins by spending three times
  as much is a different claim, and is reported as that claim.
- **collateral** — files touched outside the capability's own module, and
  whether the full fast suite is still green after the attempt.
- **specialist calls** — count and target, per arm. **Diagnosis only, never a
  target.** It can be driven to any value by writing "delegate" into a brief,
  so it explains a result and never scores one. Reported for arm G as well
  (self-delegation), because an endpoint reported for one arm only is an
  endpoint chosen after the fact.

## 5. N, stated in advance, and what it cannot detect

**16 tasks** (8 per pool) × **2 arms** × **2 repeats** = **64 attempts**.
Paired per task, bootstrapped over tasks, 10,000 resamples.

At 16 pairs this design can detect a difference of roughly **30 percentage
points** in completion rate. **It cannot detect 10.** If the true effect is
small, the interval will cover zero and the correct conclusion is "not
distinguishable at this N", not "no effect".

Budget: an agent run in the recent waves consumed 1–5 M input tokens, call it
3 M. 64 attempts is therefore of order 190 M tokens against a measured ceiling
of 50 M per key per day over three keys — two nights, not one. Repeats exist
because the same model on the same task does not do the same thing twice;
with one repeat a single stall would be indistinguishable from a real
difference.

## 6. Blind scoring and blind review

The runner writes each attempt into a directory named by an **opaque id**. The
arm lives in a separate mapping file that the scorer never opens. "Completed"
is decided mechanically; where a human or a reviewing agent judges anything,
that reviewer is given the diff and not the arm.

The scorer is itself an instrument, so it has tests that drive it against
fixtures — a capability connected, one deleted properly, one deleted with its
tests left behind, one where the instrument was touched, one where a test
became a skip — and each test must fail when its check is removed. An
instrument that reports success without doing its job is the defect class
this whole corpus is drawn from.

## 7. What will not be measured, and why

- **Number of landings, fixes, or PRs.** Driven by splitting work.
- **Any self-report of improvement**, from an agent or from me.
- **A pass rate under a judge being tuned at the same time**, as a target.
- **Anything computed by the same code path that produced the change.**
- **Specialist-call count as a success measure** — see §4.
- The sample is drawn **once**. If the first night's numbers are
  uncomfortable, the remedy is an addendum, not a redraw.

## 8. Provenance

The six design holes this protocol closes — the information confound, task
selection, gameable tests, who decides "landed", nondeterminism, and cost as a
second axis — were pointed out by the operator who ran the MANTA freeze, on
2026-11-20, against the first draft of this design. That draft would have
produced a number. The cases behind each are in
`DELFIN_RUNDE3/coord/goodhart-principles.md` of the coordination repository,
and the first draft's own flaw is §0 of this file.

**Not measured and not verifiable from here:** whether the specialist
architecture helps on the chemistry work the five specialists exist for (§0);
whether the result transfers to a different model; and whether the prompt-byte
confound of §2 accounts for any difference found.
