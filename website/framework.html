01 / THE BUILDING BLOCKS

A model inside
a working system.

The language model proposes what to do next. DELFIN supplies the surrounding harness: the conversation loop, prompts, context, tool interfaces, permissions, execution records and checks. The chemistry engines remain separate programs; their outputs supply evidence for the agent’s conclusions.

Read the architecture as a linear sequence

One session, several entry points

The terminal and dashboard expose agent sessions. The engine manages role prompts, history and task state; backend adapters handle model communication and tool-call loops. Anthropic, OpenAI, KIT and local OpenAI-compatible routes are represented in the client layer. Capabilities and enforcement details depend on the selected backend.

A relevant tool surface

Tool groups are advertised according to workspace context and configuration. Chemistry and document tools can be offered where relevant, keeping unrelated schemas out of each request. Advertising a tool and authorising its execution are separate decisions: hiding a schema does not replace the execution gate.

Where subagents and swarms fit

A subagent has its own message history, budget and tool surface. Presets include exploration, planning, code review and general work. Permissions derive from the parent; inherited sandbox and deny rules remain in place. The parent receives a report, and report-verification code compares supported claims with recorded actions.

Swarm coordination adds multiple sessions, workspaces, messages and status events. Its lead tools wrap the same service operations used by the CLI and dashboard. In the documented lead contract, state-changing coordination actions require the person’s confirmation. Separate contexts reduce interference; the parent still has to assess and integrate the results.

Read the implementation: session engine, backend and execution layer, tool groups, subagents and swarm lead.

02 / FROM REQUEST TO EVIDENCE

What happens
during a task?

A chemistry request and a code change use different tools, but share the same basic discipline: establish the goal, inspect the relevant material, execute within scope, and check the outcome.

Read all six stages

  1. Establish the task and working boundary

    Identify the workspace, requested deliverable and constraints. Project instructions, session state and available tools provide the working context. A saved note is background information; it does not grant new permission.

  2. Read before choosing an action

    Inspect source files, documentation, calculation folders or earlier evidence. A chemistry workflow should use DELFIN’s existing tools and templates where appropriate, preserving their settings and provenance.

  3. Propose a bounded next step

    The model requests a tool call. Before execution, the gate evaluates the action, target paths and permission rules. A request may proceed, ask the person, or be refused. A model-generated plan does not authorise itself.

  4. Execute and retain what actually happened

    Tools return outputs, errors and execution status. Calculation evidence can be collected from CONTROL settings, program inputs, program outputs and submission records. These records are distinct from an agent’s narrative about the run.

  5. Check, then recover if needed

    For code, use checks discovered from the project. For a calculation, inspect completion and scientific warnings. A failure supplies information for the next step; repairing a job or changing a method remains subject to the active permissions and the scientific question.

  6. Report the result and its verification limits

    The answer should name what was produced, what was measured and what remains unresolved. Supported claim checks can flag statements that outrun the recorded evidence. Useful experience may later enter a memory or a reviewed skill proposal.

Evidence paths: calculation records, project-derived verification recipes and turn verification.

03 / CONTINUITY WITHOUT AN UNBOUNDED PROMPT

Remember the useful.
Retrieve the relevant.

Context is finite. DELFIN separates current working state from durable facts, reusable procedures and past-session records. These carriers differ in when they are written and how they return to a model request.

Scope is a second dimension

The cross-session memory design distinguishes session, project, shipped knowledge and user scope. Its level-composition path labels the source and favours narrower context over repeated wider context. This is a recall rule, separate from the permission system.

Compaction preserves structure

In-turn compaction works on whole tool-call rounds, keeping call/result pairs together. It preserves the session prefix and recent rounds, and summarises older outcomes, touched files and refusals. It is a bounded representation of history, so exact late recall still needs measurement.

How a lesson becomes shared knowledge

Shipping a distilled lesson into the knowledge pack requires followable evidence, privacy checks, instruction checks, a valid entry template and duplicate handling. Contradictory entries are refused rather than silently replacing earlier knowledge. Shared lessons are reviewed in PRs.

Memory curation proposes merges and retirement of stale notes; retirement moves records aside. Agent-written notes are checked for instruction-channel content and recalled inside an untrusted-data boundary. A useful memory must remain evidence, rather than becoming a standing approval.

Design and limits: memory mechanisms, memory scopes and shipping gates and in-turn compaction.

04 / SELF-VALIDATION AT DIFFERENT LEVELS

Check the work.
Then check the claim.

“The command ran”, “the test passed”, “the calculation is usable” and “the answer is supported” are different conclusions. DELFIN has separate mechanisms for these questions. Their coverage depends on the tool route, available records and configuration.

01 / EXECUTIONDid the observed work support completion?

The turn-verification account reads tool calls and results: edits, program runs, tests, checks and outcomes. The live turn loop and benchmark process metrics share this event accounting. This lets supported completion and test-claim checks compare the answer with what was actually observed.

Verification recipes discover check commands from project files and CI; discovering a recipe does not run it. Evidence-freshness checks associate test results with a worktree state, so an older green run is not silently treated as verification of changed code. The freshness fingerprint is a practical state check, not a cryptographic proof of all file contents.

A green command only establishes what that command checked. Missing execution evidence remains missing evidence.

02 / SCIENTIFIC OUTPUTDid the calculation finish in a usable state?

The read-only ORCA result critic checks normal termination, SCF convergence, geometry convergence, imaginary frequencies, transition-state expectations and spin contamination. A normally terminated calculation can still carry a warning or an error relevant to the scientific interpretation.

For example, an optimised structure without a frequency calculation is not confirmed as a minimum by that optimisation alone. The critic reports the issue; it does not edit the calculation or weaken convergence to obtain a green status.

These diagnostics detect specified failure modes. They do not establish that the chosen method, molecular model or physical assumptions answer the research question.

03 / ANSWERCan a reported result be traced to evidence?

The scientific claim checker scans supported numerical values with units against evidence excerpts. It checks for missing provenance, missing level-of-theory information and omission of known result-critic warnings. Values explicitly marked as estimates are handled differently from reported calculations.

Additional verification guards address supported ORCA keyword claims against extracted manual ground truth, source-grounded code claims and other recognised inconsistencies. The engine can surface caveats or correction feedback rather than leaving an unsupported statement unqualified.

These are structured and pattern-based checks with defined coverage. A numerically matching value alone does not prove an entire argument correct.

04 / EVALUATIONDoes the agent satisfy an independent task?

Benchmark tasks define prompts, expected and forbidden signals, optional numerical values, acceptance checks and budgets. The runner records a trajectory; scoring is computed from recorded evidence and task criteria. Method metrics also examine evidence reading, claim checking, scope and honest reporting of verification limits.

Workflow evaluation can layer trajectory grading, run-evidence checks and answer-claim checks. The nightly path distinguishes a failed attempt from an unmeasured attempt, such as an engine that never started. An unmeasured run is excluded from quality scores and named in the report.

A benchmark measures its task population and rubric. It is not a blanket certificate for every workflow or model.

The change-scoped test-honesty scanner asks another question: do the submitted tests measure the new behaviour? It can flag patterns such as candidate switches not exercised by the tests in the change, or tests tied to a builder’s temporary copy. Its findings are scoped to the supplied change records.

05 / OUTCOMEWhat does the run report to a program?

A headless run does not answer only in prose. It ends with a stop_reason and a process exit code, so a supervisor, an orchestrator or a script can act on the outcome without parsing text: done 0, incomplete 9, needs_approval 4, refused 5, max_turns 6, budget 7, timeout 8, error 1, and degenerate_test_loop 10 for a turn the engine stopped because the model kept editing and re-running a test that failed identically. Exit codes 2 and 3 mean no turn ran at all — a usage error, or an engine that could not be built — so there is no result object to read.

incomplete is the distinction that matters for unattended work: a turn that ended of its own accord with work left. Its task ledger was still open, the ledger could not be read, or the model announced a tool call and made none. Such a run may be resumed exactly as a finished one may, and it is kept distinct from both a failure and a success: a turn that stopped with its task list still open should not read as a completed one.

The result record carries a schema version, and a reader compares it before trusting the rest. Adding a key is not a version bump; changing what a key means is.

These codes describe how the turn ended, not whether the science is right. That is what the four questions above are for: a run can exit 0 and still carry a calculation nobody should use.

Check implementations: turn outcome, evidence freshness, result critic, scientific claims, verification guards and benchmark scoring.

05 / HOW EXPERIENCE CHANGES THE SYSTEM

Observe. Propose.
Measure. Review.

DELFIN implements several complementary improvement paths. An observed failure can become a test case; a demonstrated procedure can become a skill proposal; a harness change can become a controlled comparison. Each path has its own entry conditions and adoption step.

OUTCOMES → TASKS

Make recurring failures reproducible

The evaluation loop groups recorded failures by task class, error type and mode. Recurring patterns generate draft benchmark tasks and a report. Maintainers fill in the expected behaviour before those drafts become an evaluation instrument.

Default outcome mining and report generation are model-free file analytics. A live benchmark is a separate, cost-bearing run; the default evaluation pass does not launch it.

EVIDENCE → SKILLS

Retain a demonstrated procedure

Session-end learning can propose a reusable skill when a finished session has suitable evidence, such as observed tests, a verified job or a verification recipe. The proposal is checked and stored outside the active skill discovery path.

Only human acceptance activates it. Missing or failing safety checks block the proposal. Proposal generation and adoption are distinct operations.

CONTRAST → HARNESS EDIT

Improve guidance under matched conditions

The harness-improvement round targets a weak task family and evaluates candidate guidance changes using matched tasks, seeds and model conditions. Candidate edits are restricted to allowed skill or tool-guidance text; protected paths, code and knowledge-pack edits are refused by this mechanism.

The round produces observations, candidate verdicts and evidence-backed lessons. It applies no edit automatically. Adoption is a reviewed PR with a separate holdout check: the target family should improve without another family falling.

Bounded work loops are another mechanism

A reusable loop file declares a goal, steps, trigger, check, optional metric, permitted change scope, protected measurement files and budgets. The user confirms the exact definition before it runs. An agent may propose the loop but cannot confirm it through its own tool calls.

The controller supports limits on iterations, wall time and tokens, with stop conditions such as plateau or repeated failures. Measurement files and the check itself are protected against being rewritten into a passing condition. This controls repeated work; it does not turn a configured metric into independent scientific truth.

Improvement paths: outcome evaluation, session learning, proposal acceptance, harness comparison and bounded loop definitions.

06 / THE MEASURE MUST STAY FIXED

What would count
as an improvement?

A plausible explanation is a hypothesis. A defensible comparison also needs a known population, a stable instrument, actual exposure to the candidate change and an honest treatment of noise. DELFIN provides experiment records and paired-comparison utilities for this discipline.

Read the six conditions for a defensible comparison

  1. State the expectation before measuring

    The experiment API records a hypothesis, reason chain, switch, expected effect and interpretation before accepting measurements. Its lifecycle makes pre-registration a condition of recording.

  2. Prove the candidate is the change being tested

    The switch-based experiment protocol requires a default-off candidate. Switch-off output must be byte-identical to baseline. A reach check requires the switch to be read and to affect exactly the declared target cases; running a no-op is not evidence for the change.

  3. Keep population and instrument comparable

    Instrument stamps cover declared code, judge, tools and relevant environment. Paired comparisons additionally inspect item identities, duplicates, provenance and the declared change axis. Differences outside that axis, unknown defaults or inactive switches can prevent a conclusion.

  4. Inspect regressions and run-to-run variation

    Use absolute counts and per-case outcomes. The experiment noise gate uses benchmark statistics and requires blocker classification. The separate paired-comparison utility uses a conservative never-worse rule: an individual regression can block it regardless of aggregate significance. These are different checks, not one universal score.

  5. Evaluate on held-out tasks within budget

    The nightly holdout path requires a readable external seed file and does not disclose its value in the report. Practice runs use a public seed. Its accounting checks estimated core-hour spend before starting each instance; an unavailable run is reported as unmeasured.

  6. Hand over the evidence for a human decision

    The experiment lifecycle proceeds from verdict to human review, recorded approval and landing. The paired comparator’s strongest result is “needs human check”, not permission to land. Broader code changes still follow their own repository review and verification process.

ILLUSTRATIVE CANDIDATE / NOT A MEASURED RESULT

A clearer instruction for reading an ORCA output

Hypothesis: a guidance change makes an agent inspect convergence before reporting an energy. Compare baseline and candidate on the same task instances and model, verify that the new guidance is reached, and inspect both scientific warnings and unrelated task families. If the candidate only changes wording, or a regression appears elsewhere, that matters to the verdict.

This page describes mechanisms and an example hypothesis. It does not claim a benchmark gain from this website change.

Long sessions need their own evaluation

The long-horizon benchmark defines tasks with planted facts, early decisions, refusals, restarts and goal-focus requirements. Metrics examine late recall, constraints still honoured, repeated work, drift, compactions, cost and time. Replay mode exercises the record and metric pipeline deterministically; operator-run live sessions evaluate actual model behaviour.

A replay passing is not a measured live-model gain. Reports need the task, model, method and source revision to make comparisons interpretable.

Measurement contracts: experiment discipline, paired comparisons, nightly holdout and budgets and long-horizon evaluation.

07 / CONTROL IS PART OF THE ARCHITECTURE

Autonomy within
an explicit boundary.

Permission modes, path and command rules, protected files, host isolation and network controls act at different layers. The gate evaluates proposed actions before execution. OS-level confinement depends on the host; the documented threat model distinguishes these guarantees rather than treating a prompt instruction as a sandbox.

Protect the decision channel

An agent cannot approve its own pending request. The permission system, confirmation routes, safety settings and shared knowledge have protected write paths. Recalled memories, fetched pages, tool results and delegate reports are treated as data with provenance, rather than as new authority.

Keep claims proportional to coverage

Backend routes differ in the evidence available to runtime guards. Keyword retrieval can miss relevant memories; parser and claim checks cover recognised cases; benchmarks cover their declared tasks. The model provider also receives the context supplied to it. These limits belong in the engineering model.

Inspect the boundary and the evaluation instrument

From an installed DELFIN environment, these commands inspect configuration or perform deterministic checks. The command explanation does not execute the proposed command, and the optimisation check does not run a live model benchmark.

delfin-agent capabilities
delfin-agent gate explain -- python analysis.py
python -m delfin.agent.optimize_check --strict

The optimisation preflight checks task integrity, manual-backed ground truth and required role prompts. Passing it is a precondition check, not a performance measurement.

What holds, and where it stops

Four mechanisms carry the boundary, and each is worth naming because each fails differently. A single egress route is the one way out to the network for a contained command; it runs in the agent process, outside every sandbox, so the command cannot reconfigure it. A socket guard lets such a command reach only the local servers it started itself — a service already running on the machine is not part of its reach. An append-only audit record is hash-chained, and a single command verifies the chain rather than asking anyone to trust it. A change journal records what a turn wrote, so an edit can be taken back.

Several people can share one installation: each gets their own home, their own sessions and their own API key, and one person’s phone never reaches another’s sessions. The honest limit is in the implementation’s own words: everyone is the same operating-system user, so this is an application-level boundary and not one the kernel enforces. Where that matters, one account per person is the stronger answer — the documented model says so rather than implying otherwise.

Full scope and host-specific limits: security model. Instrument preflight: optimisation checks.
